## 2. 対象登録先と登録番号の拾い方

### 対象登録先

**推奨案**: 最初の自動取得は ClinicalTrials.gov API v2 の番号指定照会に絞る。WHO ICTRP と jRCT は番号候補・未対応表示までとし、自動取得は次の候補として保留する。CT.gov の実現性が確認できなければ、公開時期を優先して不明な API を代用せず、手動入力方式への設計変更を所有者へ戻す。

| 選択肢 | 利点 | 制約・採否 |
| --- | --- | --- |
| CT.gov から開始 | 一つの取得経路でスナップショット・対応付け・D5 支援を検証できる | 推奨。API v2 の URL、認証要否、フィールド、履歴取得、レート制限、拡張からの疎通、再利用条件はすべて要確認。 |
| CT.gov / WHO ICTRP / jRCT を同時対応 | 対象試験の範囲を広げられる | 各 API の提供状況、取得許可、重複登録の扱い、日付の意味が要確認。初回の範囲には含めない。 |
| CSV / XML / 登録 PDF の手動取り込みを中心にする | API に依存せず原本を固定できる | 代替案。tiab の CSV 列は参考になるが、配布形式の現行仕様は要確認。登録 PDF は既存 `document_role=registration` を利用可能。新しい汎用 CSV / XML インポータは初回案に含めない。 |

取得は利用者が番号を選んで「登録情報を取得」を押したときだけ行う。取り込み・画面表示・番号検出をきっかけに自動照会しない。タイトル検索や外部への抄録送信は初回案に含めない。

### 登録番号候補

**推奨案**: 既存の検出を取り込み時の初期値として維持し、突き合わせでは study 配下の本文・取り込み済み抄録 PDF の抽出テキストから候補一覧をローカルで作る。候補ごとに正規化 ID、出所文書、出現位置・周辺文を示す。抄録が独立した文字列として利用可能な経路は実装時に確認し、存在しない素材を外部から自動取得しない。テキスト層がない PDF は自動検出不能と表示し、手入力を許可する。

- 選択前は `Studies.registration_id` を第一候補として示す。複数候補がある場合も自動的に同一試験と確定しない。参考文献内の番号や多試験の報告を人が除外できるようにする。
- 一つの study に複数登録がある場合は登録ごとの関連付けを持ち、`registration_id` に連結して保存しない。主番号の変更は既存の S3 編集を使い、取得だけでは上書きしない。
- 異なるレジストリ間の別名関係は人が確認する。形式一致は実在や同一試験の保証ではない。ID から許可済みホストの照会 URL を構築し、入力 URL や登録レコード内の任意 URL を自動 fetch しない。

代替案は「既存の一件検出だけを利用」（実装は小さいが複数登録や誤候補を説明できない）と「LLM で番号を推定」（本文の外部送信と誤生成を増やす）。候補一覧と手動確認を推奨し、番号検出に LLM は追加しない。

## 3. 突き合わせる項目と比較の規則

**推奨案**: 登録側の項目と、現在の annotator が確認する論文側の値・引用を並べる。アウトカムの対応は人が確定し、決定論的な一致候補は提案までにとどめる。登録側を正解として論文側の値を書き換えない。

| 項目 | 表示・比較案 | 限界と代替案 |
| --- | --- | --- |
| 主要・副次アウトカム | 登録の区分・名称・定義・尺度と論文側の報告を並べ、一対多・多対一を許す対応表で確認する。区分の変更、未対応、追加報告を区別する | 名称の完全一致のみでは尺度変更を見落とす。LLM の意味対応は代替だが初回は採用しない。副次・その他の区分や API 上の構造は要確認。 |
| 評価時点 | 原文の期間、起点、単位を残し、同じ起点の明白な単位変換だけを候補に使う | 「12 weeks」と「3 months」は自動一致させない。時点がない側は「情報不足」。自由記述のみの並列表も代替だが、構造化できる範囲は比較する。 |
| 予定症例数 | 登録原文と予定 / 実績の区分を保存し、論文の目標数・無作為化数・解析数を別々に表示する | `Enrollment` の数字だけから予定数と決めない。予定と実績を直接不一致にしない。API で区分・過去の予定値を得られるか要確認。数字だけの差分表示は不採用。 |
| 登録日と試験開始日 | 初回提出日、初回公開日、開始日、主要完了日、更新日を意味別に保持し、存在する項目だけ表示する | tiab に `First Posted` と `Start Date` の扱いはあるが、初回提出日など API 側の提供可否は要確認。公開日を登録日と同一視しない。開始日のみとの比較で事前登録と断定しない。 |

日付は原文と精度（年 / 月 / 日）を保持する。精度が違う場合は可能な期間として比較し、期間が重なると「前後不明」、完全に分離するときだけ順序を示す。不正値・未記載・取得不能を区別し、日付を補完して確定値にしない。

比較結果は「一致候補」「差異候補」「対応未確定」「片側に記載なし」「比較不能」と、人の「確認済み / 保留」を別に持つ。「片側に記載なし」は取り込んだ資料内での状態であり、研究全体の未報告や選択的報告の証明ではない。論文のスキーマに比較項目がない場合は追加を案内し、登録側の値でセルを自動生成・確定しない。

**版の選択**: 取得日時、登録側の更新情報、取得できた版の識別子を表示する。初回取得の最新版は「現在の登録」であり「試験前の登録」と呼ばない。過去版を取得できる場合も選択は人が行い、選択した版を固定する。API に過去版がない、または取得できない場合は「事前指定を確認できない」と示し、登録 PDF・プロトコル・SAP の確認へ誘導する。履歴を自動的に試験開始前へさかのぼる案は、API の可否と方法論を確認するまで保留する。

## 4. RoB 2 D5 と根拠の提示

**推奨案**: S8 に「登録情報との突き合わせ」カードを設け、対象結果を明示して SQ ごとの参考資料を表示する。既存テンプレート・抽出プロンプト・RoB の決定ロジックは初回案では変更しない。

| 既存 SQ | 提示する根拠 | 自動では決められない点 |
| --- | --- | --- |
| `rob2_sq5_1` | 選択した登録版、日付、プロトコル・SAP の論文側引用と参照先 | 解析計画が非盲検アウトカムデータ利用前に確定したか。単に登録が古い、主要アウトカムが一致、だけでは Yes にしない。 |
| `rob2_sq5_2` | 対象結果に対応する尺度・定義・時点、登録内の他の測定候補と論文の引用 | 複数候補から結果に基づいて選択したか。差異があるだけで Yes にしない。 |
| `rob2_sq5_3` | 登録や SAP に明示された解析候補と、論文で報告した解析の引用 | 初回の比較項目だけでは複数解析からの結果に基づく選択を確認できない。記載がなければ情報不足を示す。 |

`rob:d5_reporting` は study 全体の base。結果が異なる場合は、既存の結果単位オーバーライド（例: `rob:d5_reporting|outcome:insomnia|time:12w`）を人が宣言し、その結果だけに根拠を関連付ける。カードの対象結果と判定先が一致することを保存時にも確認する。SQ テンプレートがなければ比較だけ利用でき、導入案内を出して自動挿入はしない。

### PDF 引用と登録スナップショットの境界

- 論文側は既存 `Evidence` / 有効な `QuoteSets` の引用を参照し、出所 PDF へのハイライトを使う。独立入力では自分の引用だけを使う。
- API 側は保存した原本中の項目位置（内部の項目パスと配列位置）、逐語文字列、スナップショット ID を持つ。原本の該当箇所へ移動して表示し、現在の外部ページへのリンクは補助にする。表示テキストは HTML として実行しない。
- API データには架空の `document_id`・ページ・PDF の `anchor_status` を付けない。登録文字列の原本内検証は別の状態（確認済み / 該当なし / 原本なし）にし、PDF の `exact / normalized / fuzzy / failed` とダッシュボードの失敗率へ混ぜない。
- 人が既存 SQ を判定するときに、見ていた比較版・登録スナップショット・項目の識別子を追記記録する。API の識別子を `seen_evidence_ids` に入れず、`Decisions` の末尾への専用参照列追加を提案する。undo を含めて既存履歴を残し、再取得で以前の判定根拠を差し替えない。

代替案は「登録 JSON を PDF に変換し既存 Evidence に一本化」（原本の項目位置と PDF の照合結果が混同される）と「LLM に登録と論文を渡して SQ を自動提案」（新しい AI 入力と妥当性検証が必要）。初回は出所を分けた人の判定支援を推奨する。

## 5. Sheets と Drive の保存設計案

**推奨案**: `Evidence` の対象を広げず、次の三つの追記型タブを設ける。名称・列は設計レビューで確定する。現行のタブ構成は [sheetsSchema.ts](../src/domain/sheetsSchema.ts) を根拠とし、古い文書のタブ総数を前提にしない。

| 新タブ案 | 粒度と主な列 | 更新・読み取り規則 |
| --- | --- | --- |
| `RegistrySnapshots` | 一行 = 一取得原本。`snapshot_id`, `registry`, `registration_id`, `source_url`, `retrieved_at/by`, `source_version`, `source_updated_at`, `raw_ref`, `raw_hash`, `parser_version` | 原本は Drive の専用配下に保存し、大きな応答を Sheets の一セルへ詰めない。解析用データにも原本の項目パスを残す。再取得は新 ID で追記し、旧原本は不変。外部の版情報がなければ空とし、取得日時を版の日時に代用しない。 |
| `RegistryLinks` | 一行 = study と登録の関連付けイベント。`link_id`, `study_id`, `registry`, `registration_id`, `snapshot_id`, `action`（関連付け / 解除）, `created_at/by`, `note` | 複数登録を許容し、解除は追記する。`Studies.registration_id` と独立して保持する。グルーピングで新 study_id になったら関連付けを自動転記せず、旧履歴を示して再確認する。 |
| `RegistryComparisons` | 一行 = 対応表の版に属する比較項目。`comparison_id`, `set_id`, `study_id`, `annotator/type`, `schema_version`, `snapshot_ids`, 論文側 `field_id/entity_key` と値・引用の参照、登録側の項目パス・逐語文字列、候補状態、人の確認、理由、規則版、`created_at` | 一対多は項目参照の配列で表現する。論文側の参照だけでなく閲覧時の値・引用も固定し、再抽出後の表示を再現できるようにする。対応変更は新しいセットの追記。空にしたことも明示的に記録する。 |

比較セットは本文を Drive に保存して参照する方式も許容し、セル上限に達しうる配列を無制限に保存しない。完全に保存できたセットだけが有効になるよう完了印と冪等キーを定め、途中失敗したセットで旧セットを置き換えない。原本保存だけ成功しシート参照保存に失敗した場合は、同じ原本を使って再保存できるようにし、画面では未保存と表示する。失敗のたびに外部へ再照会しない。

`Decisions` の専用参照列は `registry_comparison_ids`（見ていた `comparison_id` の配列）を候補とし、判定時点を固定する。値がない旧行は参照なしとして読む。既存 audit.csv への末尾列追加と、登録比較の別添ファイル（原本参照・項目パスを含む）を実装範囲に含め、PDF の Evidence 列は維持する。登録情報だけで `StudyData` / `ResultsData` を書き換えない。

新タブがない既存プロジェクトは未利用として読めるようにする。初回保存でタブを追加する方式と旧拡張が追加列を読めるかを fixture で検証する。未利用プロジェクトに強制移行を要求しない。登録原本はプロジェクト内の共有資料となるが、比較の対応付け・メモ・確認結果は annotator ごとに分離する。独立入力では他者や AI の対応表を表示・初期値に利用せず、自分の未確認から始める。裁定で他者の対応を表示する場合は既存の裁定開始条件を守る。

代替案は「Evidence に source_type / URL / registry 列を追加して統合」（PDF のビューア・引用解決・監査出力など全読取側の再設計が必要）と「Studies.note に JSON を保存」（小さいが複数版・annotator・判定時点の追跡に不向き）。新タブ案は保存処理が増えるが、出所と追記型の監査を明確にできる。

## 6. 外部送信・権限・同意の影響

確認した現状は次のとおり。

- [manifest.json](../src/manifest.json) の `host_permissions` は Google API と Gemini / OpenRouter / Anthropic。登録先の固定権限はない。`optional_host_permissions` に `https://*/*` があるが、これ自体は個別ホストへのアクセス許可ではない。
- [aiDataConsent.ts](../src/lib/llm/aiDataConsent.ts)、[aiDataConsentDialog.ts](../src/app/ui/aiDataConsentDialog.ts)、[aiDataConsentStore.ts](../src/lib/storage/aiDataConsentStore.ts) は LLM 呼び出し前の同意を扱い、現在の版は 3。送信内容の説明は [ja.pages.ts](../src/lib/i18n/ja.pages.ts) にあり、AI の送信先と保存を説明している。
- [hosted/privacy-policy.html](../hosted/privacy-policy.html) は冒頭・概要で Google と BYOK LLM の間の流通を説明し、データ表、Google データの第三者への送信、保存・削除も記述している。登録照会を加えると「3 者のみ」などの限定表現を同期する必要がある。

**推奨案**: 登録照会は LLM 同意と独立した告知・操作にする。既存の optional 権限の範囲から確認済みの登録先ホストだけを要求し、拒否しても保存済み資料と既存機能を使えるようにする。Chrome の権限許可と、何を送るかの説明は別であり、片方をもう片方の代用にしない。実際の接続先ホストとリダイレクトは要確認。

| 経路 | 送信・保存の提案 |
| --- | --- |
| ブラウザ → 登録先 | 選択した登録番号だけを検索内容として送る。論文本文・抄録・プロトコル・メール・シート ID・Google OAuth トークン・LLM キーは送らない。接続元 IP 等の通常の通信情報は相手へ届く旨を説明する。 |
| 登録先 → ブラウザ → 利用者の Drive / Sheets | 公開登録の原本、取得時刻、比較・確認履歴をプロジェクトへ保存する。共有相手からも参照可能であること、削除方法を説明する。開発者のサーバーは設けない。 |
| ブラウザ → LLM | 初回案の取得・比較には新しい LLM 呼び出しを加えない。将来登録原文を送る機能を加える場合は、送信素材・ログ保存を明記し、`aiDataConsent` の説明と版を更新して同意を取り直す。 |

初回案では `aiDataConsent` の対象となる AI 入力を増やさないため版を据え置くことを推奨する。ただし説明に登録照会を統合する案を選ぶ場合は、送信先・内容が実質的に変わるので版を上げて再同意と取消の挙動を定義する。所有者がどちらを採るか決める。

代替案は「登録先を固定 `host_permissions` に追加」（任意操作の前に権限が増える）と「既存 AI 同意へ包括的に統合」（AI を使わない照会にも AI 同意が必要になりやすい）。任意権限と独立告知を推奨する。Google の OAuth スコープは増やさない。

実装時は `hosted/privacy-policy.html` の日英の概要・表・第三者送信・保存削除・データフロー説明と図、`hosted/help.html` の日英、取り込み画面の外部送信先の注意も同期する。今回これらは変更せず、設計確定後の issue に含める。

## 9. 設計レビュー後に起票する実装 issue の分割案

以下は起票案であり、まだ実装着手や API 利用を承認したものではない。依存順は A → B → C → D → E。公開は E の確認後にまとめる。

| 仮題 | 範囲 | 受け入れ条件 |
| --- | --- | --- |
| A: 登録取得の API 契約確認と UI・保存仕様の確定 | 所有者が外部仕様を確認し、requirements と ui-states に承認内容を移す。API のフィールド対応表、権限、同意方針、保存・出力列を確定する | 確認日・公式資料の出典を記録し、API の未対応項目を明示。最新版と事前版を区別する方針が確定。所有者の設計レビュー完了が記録され、実装前に spec が存在する。 |
| B: 登録候補と取得スナップショットの保存 | 候補一覧、複数関連付け、確認済みホストの取得、Drive 原本と新タブ、再取得・解除・失敗処理 | 候補なし・複数・未対応・手入力・拒否・中止・未該当・不正応答・通信失敗・部分保存を fixture / fake で検証。操作前の外部通信ゼロ、許可ホスト以外へ送らない。旧プロジェクトを開け、再取得で原本を失わない。 |

## 10. 実機 / 実 API 確認の計画

本設計書の作成自体は実 API を使わない。実装後は所有者の明示的な実機確認として、公開登録番号を使い次を記録する。未実装のためすべて未実施。

1. 確認済み API へ拡張オリジンから照会できること。任意権限の拒否・取消・再許可と、送信内容が登録番号に限定されていることを確認する。
2. 主要・副次アウトカム、時点、予定 / 実績、日付と精度を登録画面・取得原本と照合し、欠落や最新版だけの場合の説明を確認する。利用可能なら過去版も確認する。
3. 未該当、通信制限・失敗、応答仕様変更時に古い資料を維持し、利用者の明示操作で再試行できることを確認する。障害は可能な範囲を fake で再現し、実サービスへ負荷を掛けて作らない。
4. Drive / Sheets への保存、再入場・別端末・共有時の復元、独立入力の分離、D5 判定時の原本参照と出力を確認する。
5. 本番に相当する日英の告知・ヘルプ・プライバシー説明と、ネットワークの実際の送信先・保存先を照合する。

進捗は [remaining-work-plan.md](remaining-work-plan.md) の「実機 / 実 API テストが必要な項目」で管理し、確認結果を得るまでは設計やローカルテストだけで確認済みにしない。
