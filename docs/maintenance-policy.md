# 保守期の基準

2026-11-13 確定。MVP・P1 前倒し分・M1〜M4 の完了を踏まえ、保守期へ移行する。今後は不具合修正・依存更新・文書・評価を優先し、リリースの回数を抑える。M4「登録情報との突き合わせ」（[#496](https://github.com/youkiti/sr-data-extraction-plugin/issues/496)）は、保守の作業と並行して進める例外とする。

残作業と実機 / 実 API テストの一覧は [remaining-work-plan.md](remaining-work-plan.md) で管理する。

## 足さないもの・凍結するもの

| 対象 | 方針・再開条件 |
|---|---|
| 新機能 | #496 以外は原則受け付けない |
| 図の数値読み取り（[#265](https://github.com/youkiti/sr-data-extraction-plugin/issues/265)） | [#356](https://github.com/youkiti/sr-data-extraction-plugin/issues/356) の評価の物差しができるまで凍結する |
| 二段構えの抽出（[#287](https://github.com/youkiti/sr-data-extraction-plugin/issues/287)） | #356 の評価の物差しができるまで凍結する |
| LLM プロバイダの追加 | 停止する |
| RoB ツールの追加 | 停止する |

凍結対象は、評価の物差しができた時点で再開の可否を検討する。自動的に実装を再開するものではない。

## 保守として扱うもの

- 不具合・セキュリティ・データ破損の修正
- 外部 API の仕様変更への追従と依存更新
- 文書・ヘルプの修正
- ベンチマークなどの評価

プロンプトと既定モデルの変更は、次の条件を満たす場合に限る。

## プロンプト・既定モデルを変える条件

| 対象 | 変更を認める条件 |
|---|---|
| プロンプトの版上げ | ベンチマークで変更前後を比較した結果を PR に添える場合だけ |
| 既定モデルの変更 | 提供終了・改名・大幅な値上げのときだけ |

新モデルの登場や、測定していない改善の見込みだけでは既定モデルを変えない。プロンプトの版上げは、変更の狙いと比較結果を確認できる形にする。

## リリース頻度

通常のリリースは月 1〜2 回にまとめる。セキュリティ・データ破損・API 仕様変更への対応は緊急修正として、通常のリリースを待たずに出す。

## 要望の Issue を扱う手順

1. 不具合修正・依存更新・文書・評価か、新機能の要望かを分ける。
2. 保守に当たるものは、その範囲で作業する。プロンプト・既定モデルを変える場合は、上の条件を確かめる。
3. 新機能は #496 の対象かを確かめる。それ以外は原則受け付けず、この方針を理由として返答の下書きに記す。
4. #265・#287 は、#356 の評価の物差しができるまで凍結する旨を返答の下書きに記す。プロバイダ・RoB ツールの追加も停止対象として扱う。

## tiab の修正を横展開する手順

npm パッケージによる共通化は見送る。tiab-review-plugin の修正ごとに、sr-data-extraction-plugin と sr-query-builder-plugin へ移す必要があるかを確かめる。

1. tiab の修正内容と修正理由を読む。
2. 両リポジトリに同じ実装・同じ不具合や影響があるかをそれぞれ確認する。
3. 移す必要がある場合は、対象リポジトリごとに Issue を作り、元の修正と必要な対応・検証を記録する。
4. 確認結果を元の Issue または PR に記録する。移さない場合も、リポジトリごとに不要と判断した理由を残す。
